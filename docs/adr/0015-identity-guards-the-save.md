# A file's identity guards the save, and reload is not a merge

Saving used to rename a temporary file over the original without looking at what was already there. Two things followed from that. A file somebody else had rewritten was silently replaced by our version, which is how an editor eats work. And because the document is a read-only mapping of that file, a file that shrank underneath the editor could be read past its end — the mapping is safe from *us*, not from a concurrent truncation.

So the document now records its **identity** when it is opened: the size and the modification time. Before writing, the identity of the file on disk is read again, and a mismatch stops the save and asks a question — `[r]eload`, `[o]overwrite`, `[c]ancel` — instead of deciding on the user's behalf. Identity rather than content, because comparing content means reading the whole file on every save, which a 1 GB file cannot pay for; the two numbers are one `stat`, and a mismatch is a question rather than a verdict, so a false positive costs one keypress. After a save the identity is recorded again, because the rename replaced the file.

The question is the second kind the prompt can ask (ADR 0014): a **choice** rather than text, answered with one letter. That is deliberately the same surface as go-to-line — one place owns the keyboard, one label, one `Esc` — rather than a second widget that has to re-learn how to be modal. A choice prompt has no caret, because there is nothing to type.

Reload is an explicit **not-merge**. The overlay is dropped, and so is the undo journal, because every position in it referred to the document that just went away; keeping it would mean undoing into a file that no longer exists. Reloading therefore costs the user their unsaved edits, and the message says exactly that instead of a cheerful "reloaded". Overwrite is the inverse trade: the user's buffer wins, and the other writer's version is gone.

One platform detail is worth recording because it shapes what this protects against. On Windows, a file with a live mapping cannot be opened for writing at all — an attempt fails with "the requested operation cannot be performed on a file with a user-mapped section open". So while zeno is running, the realistic way another program changes the file is to write a new file and **rename** it over the old one, which is what git does and what zeno's own save does. The guard catches that, and it catches deletion (a missing file simply gets recreated). On Unix a plain in-place write or truncation is possible, and there the guard is not only about lost work but about not reading a mapping that a truncation invalidated.

What is *not* covered: the check happens when the user saves, not continuously while they type, and two edits that keep the same size and land within the filesystem's timestamp resolution would look unchanged. Continuous watching (and re-mapping on shrink) is the completion of this idea, not a different one; the spec asks for the editor to say so while the file is open, and today it says so at the moment it matters most.
