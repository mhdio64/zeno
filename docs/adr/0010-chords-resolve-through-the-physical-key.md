# Chords resolve through the physical key, not through the character

A chord is `Ctrl` plus a key, and the obvious implementation matches on the character the terminal reports: `KeyCode::Char('s') if ctrl`. That implementation is broken for most of the world. On Windows the console translates the keystroke through the **active keyboard layout** before handing it to the application, so `Ctrl+S` arrives as the character on the S key of whatever layout the user is typing in — `'س'` on Persian, `'ы'` on Russian, `'σ'` on Greek. The chord silently stops matching, and every binding in the keymap is dead while plain typing still works, which makes the failure look like a broken save rather than a broken binding.

The decision is that a binding on a letter chord identifies the key **physically**: the reported character is resolved back to the virtual key that types it (`VkKeyScanW` on Windows, the control byte arithmetic on terminals that send VT sequences), and only that virtual key decides which command runs. Two consequences follow. Bindings are compared on key identity, never on the character, so a rebinding UI must record keys the same way. And a chord whose character cannot be resolved to an ASCII letter does not fire at all, rather than firing on a guess — a silently ignored chord is a bug report, a chord that runs the wrong command is data loss.

The prototype found this because it was driven through a real terminal on a machine whose layout is not Latin. It is the kind of defect that no unit test written against synthetic key events will ever catch: the events in the test are the ones the author imagined, not the ones the console sends.
