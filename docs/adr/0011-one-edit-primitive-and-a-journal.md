# One edit primitive, journaled, instead of snapshots

Undo has to exist in a v1 editor, and on a 1 GB file it cannot be built the obvious way: a snapshot per keystroke costs the size of the file, which is the exact cost the whole design exists to avoid. So the document has exactly one mutation primitive — replace the text in a range with a string — and every change on top of it is recorded as that edit: what range was replaced, what was removed, what was inserted. Undo applies the inverse edit; redo applies it again. Memory is bounded by how much the user typed, never by the size of the file.

The important part is that there is *only* that one primitive. Typing is an empty range replaced by a character, Enter is an empty range replaced by a newline, Backspace is a one-character range replaced by nothing, joining lines is the range across the line break replaced by nothing, and duplicating a line is an empty range replaced by the line and a newline. Because all of them are the same shape, one journal reverses all of them without any command knowing that undo exists, and the operators in the keymap will need no new undo machinery when they arrive. Adding a second writer later — a paste path, an indenter, a bulk replace that touches the model directly — would silently create edits that cannot be undone, so the rule is that nothing else may write.

Adjacent single-line insertions are folded into one journal entry so that typing a word is one undo step rather than one per letter, which is what users expect; a newline, a deletion, or a move to another position ends the run. The cost of this design is that the journal is a stack and cannot represent a branched history, which is not needed for the one-file job the product is for.
