# The worker colours the viewport, and a checkpoint answers for its own version

Syntax colour is never computed on the editor's thread. syntect's syntax set takes about a millisecond to load and walking a TextMate parser over the 48,000 lines of an ordinary source file takes about 1.9 seconds, measured (docs/performance.md, finding 11) — against a first-frame budget of 50 ms and a keystroke budget of 16 ms (ADR 0007). So the editor asks: it paints plain text, sends the lines it can see to a worker thread it starts when the file opens, and colours the frame that comes back. That is the same bargain the search already made, and the spec requires it (background, cancelable, never on the input path).

The contract keeps the two honest. A request names the lines wanted, the document's version, and an epoch; each new ask bumps the epoch, and the worker abandons a request the moment its epoch has moved — sending *nothing* when it does, because an answer to a question nobody is asking any more must not displace the answer that is on screen. A result is installed only if it answers what was asked, at the version the document is still at. Lines longer than 16 KB are not painted — but the parser is still walked over an empty line in their place, which is exactly `bat`'s bargain (`too_long = line.len() > 1024 * 16`, parsed as `"\n"`), verified in `bat`'s source rather than assumed: the state still advances, so a megabyte on one line cannot open a block comment and leave the rest of the file painted as a comment.

A parser is a state machine, so a window cannot be coloured from the window alone: the walk has to begin where the parser has already been. The worker therefore keeps *checkpoints* — the parser's state at the start of every 512th line it walks past, up to 64 of them, the nearest one at or before the window's first line winning. The cost of a window becomes the distance to a checkpoint rather than the size of the file: 2.5 ms for a window 47,900 lines down, against 1.9 seconds from the top, measured.

The decision that took the longest to get right is the rule for *keeping* a checkpoint. A checkpoint is the parser's state at a line **as of the version it was built at**, so it survives exactly when nothing above that line has been written since — a question about one checkpoint and one interval. The first implementation asked a different question once per file: *what is the lowest line ever edited?* That question has an answer that never changes after the first keystroke, so one edit near the top of a large file discarded every checkpoint, on every request, for the rest of the session — rebuild, discard, re-walk, 2.8 seconds a window for ever (measured; the harness now fails if it comes back). Answering the right question needed the overlay to remember versions: every segment records the version that wrote it, `first_changed_line_since(version)` returns the lowest line written since, and a checkpoint is judged against the version it carries. The editor's colour cache follows the same rule — keep the colours above the lowest line written since they were computed — which is what stops a keystroke from blanking the viewport.

Two details are easy to break and are pinned by tests: the syntax set must be loaded from the *nonewlines* dump, because `line_text` hands the parser lines with no newline and the *newlines* dump expects them (with the wrong dump, a `#` or `//` comment never closes in 7 of 29 languages and every line below it renders comment-grey); and the paint order is syntax first, search matches over it, selection over both — the search describes what the text *means* to find, the selection describes what the user is about to act on, and neither should be hidden by a colour nobody chose deliberately.

The worker reads the document through `doc::Snapshot` — the same type the search's background scan uses, factored out of `search.rs` for the occasion: one answer to "what does a background worker see", shared bytes and index, a copy of the edits, a version to answer with.
